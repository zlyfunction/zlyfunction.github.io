Module 01 · 团队核心业务

短视频与直播推荐系统（纯新手大白话课）

很多人准备 AI Infra 面试时只背大语言模型，却忘了这个团队名字叫 Recommendation Architecture (Data-Arch-TikTok Live)。把短视频推荐的来龙去脉讲明白，是你在面试里最容易拉开差距的地方。

先说人话：短视频推荐和淘宝搜索、看新闻有什么不一样？

打开 TikTok 时你一个字都没打，手机怎么知道下一条该放什么？背后靠这 4 套核心做法：

1. 全靠动作猜喜好，没有搜索词

在淘宝买鞋你会搜“跑鞋”，但刷短视频时你只管上下滑。系统把你的每个小动作都记成信号：2 秒内划走（强讨厌）、看完甚至重播（强喜欢）、点赞/收藏/转发/点进主页（超高价值）。而且短视频消耗极快，几分钟就能刷几十条，系统必须立刻跟上你此刻的心情。

2. 多路召回：先撒几张不同的网

曲库里有几亿条视频，精排大模型不可能每条都算一遍。所以第一步召回 (Recall) 会同时撒出好几张小网：按你兴趣向量找同类（双塔模型）、你关注的人新发的、同城刚火起来的、全站热门榜、正在开播的直播间……把几张网捞上来的几千条拼在一起，再交给后面慢慢挑。

3. 特征仓库与“训练推理必须一致”

模型打分需要喂入三种信息：静态信息（视频分类、作者）、你刚看过的最近 50 条视频列表（决定你当下想看啥）、统计数字（这条视频过去 5 分钟的完播率）。工程上最容易踩的大坑叫 Training-Serving Skew（训练推理不一致）：训练时拿的是“事后整理干净的数据”，线上拿的是“实时未清洗的数据”，会导致模型一上线效果暴跌！所以工程上通常会在线上打分时就把当时用到的特征原样记成日志，直接拿去训练。

4. 为什么推荐团队也在大力做大模型？

传统推荐像“流水线小作坊”：召回、粗排、精排各跑各的模型，堆满手工特征，显卡算力加再多也很难继续涨效果。现在前沿方向叫生成式推荐（Generative Recommendation）：把你看过的视频序列当成“一句话里的词”，直接用类似 LLM 的 Transformer 架构来预测下一条该推什么——既能统一多个环节，也能像大语言模型一样靠更大算力持续变聪明！

Transformer 架构与显存账本（交互式计算器）

作为 AI Infra 工程师，不需要你会发明新 Loss 函数，但你必须一眼看穿每个算子吃多少计算量 (FLOPs)、占多少显存 (VRAM)。

图解：现代 LLM (Decoder-only) 单层数据流与热点算子

以主流 LLaMA 架构为例（重复 L 层，如 70B 有 80 层）。Infra 90% 的优化都集中在图中的两个核心块：Attention 与 FFN。

为什么都在用 GQA（分组查询注意力）？

让多个 Query 头共享同一组 K/V 头，直接把推理时的 KV Cache 体积砍掉 4~8 倍，极大缓解显存和带宽压力。

为什么用 RoPE（旋转位置编码）？

通过向量旋转注入相对位置信息，外推长文本能力强，工程上只需逐元素乘加，非常容易和 QKV 投影融合。

为什么关注 FLOPs 估算公式？

面试速算口诀：参数量 N、Token 数 T，前向计算约 2NT FLOPs，训练（前向+反向）约 6NT FLOPs！

4 张 GPU 上到底切了什么？怎么通信？

终极组合技：千卡集群里的 3D 并行怎么摆放？（面试必问硬件拓扑！）

记住一条铁律：通信越频繁的并行，必须放在带宽越高的互联里！

机内最高速：NVLink (900 GB/s)
放置 TP（张量并行，通常 TP=8）

每层前向和反向都要做 2 次 All-Reduce，通信极度密集且挡在计算关键路径上，绝不能轻易跨机器！

跨机中速：InfiniBand / RoCE
放置 PP（流水线并行）

相邻阶段之间只点对点 (P2P Send/Recv) 传递激活值，通信量最小，最适合跨机器部署。

最外层横向扩展：跨机群
放置 DP / ZeRO-1 (FSDP)

只在每个 Step 反向传播时做梯度同步，而且可以和反向计算通信计算重叠 (Overlap)，把通信延迟藏起来！

Module 04 · 线上推理高频考点

LLM 推理优化：KV Cache、Continuous Batching 与 FlashAttention

JD 里直接点名了三个词：KV Cache, Continuous Batching, FlashAttention。这三个几乎是 AI Infra 面试 100% 必考题！

Phase 1 · Prefill (预填充) Compute-Bound (算力受限)

一口气读完用户的 Prompt，吐出第 1 个字

假设用户输入 1000 个字，这 1000 个 Token 可以组成大矩阵并行做 GEMM 矩阵乘法，GPU 算力能轻松吃满。

核心指标：TTFT (Time To First Token) — 首字延迟
副产物：把这 1000 个字算出的 Key、Value 矩阵存进显存，这就是 KV Cache！
Phase 2 · Decode (自回归解码) Memory-Bound (显存带宽受限)

每次只吐 1 个新字，反复读完整个模型权重

因为下一个词依赖上一个词，只能串行一个个生成。每生成 1 个字（向量×矩阵 GEMV），就要把几十 GB 模型权重+历史 KV 从显存搬到计算单元，算力几乎闲着！

核心指标：TPOT / ITL (Time Per Output Token) — 生成速度
优化抓手：增大 Batch Size 摊薄权重读取、PagedAttention、量化、投机采样。

算法 × 硬件协同典范

FlashAttention：为什么不减少计算量却快 3 倍？

核心两招：① Tiling（分块）把大矩阵切成能塞进片上高速 SRAM 的小块；② Online Softmax 增量更新最大值 m 和分母 l，不用等整行算完再归一化，永远不把 N × N 矩阵写回慢速 HBM！

借用操作系统的经典做法

PagedAttention (vLLM)：消除 KV Cache 显存碎片

痛点：以前为了存 KV Cache 必须按最大长度提前分配连续显存，浪费高达 60%~80%。PagedAttention 把 KV 切成固定大小的 Block（如每块 16 个 token），按需分配非连续物理块，还能用 Copy-on-Write 共享相同的 System Prompt！

Module 05 · 底层硬实力

GPU 硬件架构、CUDA 与 Triton 优化入门

纯新手不需要会手写 PTX 汇编，但必须理解 GPU 线程层次、内存金字塔、Roofline 瓶颈分析，并能看懂/写出简单的 CUDA 或 Triton 算子。

图解：一张 NVIDIA GPU 内部长什么样？（线程模型 × 内存金字塔）

1. 合并访存 (Memory Coalescing)

同一个 Warp 的 32 个线程如果访问连续的显存地址，硬件会合并成 1 次缓存行读取；如果跨步乱跳，带宽直接跌几倍！

2. Bank Conflict (存储体冲突)

Shared Memory 分为 32 个 Bank。同 Warp 多个线程同时读写同一个 Bank 的不同地址会串行排队——常用 Padding（加一列）解决。

3. Roofline 与算术强度 (AI)

AI = FLOPs / Bytes。以 H100 为例，FP16 算力 ~989 TFLOPS，带宽 ~3.35 TB/s，拐点约 295 FLOPs/Byte。低于它就是 Memory-bound！

4. 算子融合 (Kernel Fusion)

PyTorch 逐个调用 Add → LayerNorm → GeLU 会反复读写 HBM。融合成 1 个 Kernel，在寄存器/SRAM 算完再写回，省下大量访存。

5. 为什么大家爱用 Triton？

OpenAI 开源的 Python GPU 编程语言。程序员只需按 Block（块）级写逻辑，编译器自动做合并访存、Shared Memory 管理和向量化，效率直逼手写 CUDA！

6. 性能剖析工具 (Profiling)

面试问“线上推理变慢怎么查”？脱口而出：PyTorch Profiler 看时间线、Nsight Systems (nsys) 查 CPU/GPU 空泡与通信、Nsight Compute (ncu) 查单算子 Roofline！
